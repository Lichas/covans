# Bugfix 记录

这里只记录值得长期保留的缺陷知识：症状、根因、修复和防回归方式。面向用户的变化写入根目录 `CHANGELOG.md`，不在这里重复发布说明。

## 2026-10-17 · 设置主题预览卡被裁成胶囊

- **症状与根因**：全局按钮胶囊规则以 `!important` 覆盖主题卡片的 14px 圆角，导致预览图与椭圆外框不协调。
- **修复与回归**：将主题预览卡从通用胶囊规则中豁免；真实 Electron UI 在浅色/深色下检查三张卡片的矩形圆角及主题切换，并遍历全部设置分类确认移除公共标题区后内容仍可访问。

## 2026-10-17 · 图片背景下用户气泡失去对比度、预览卡变成椭圆

- **症状**：选择亮色聊天背景后，单聊的用户消息变成浅底白字，难以辨认；背景预览和图库缩略图被裁成胶囊或椭圆。
- **根因**：照片背景的用户气泡规则比单聊默认深底规则优先级高，只覆盖背景而未配套调整文字；全局按钮圆角又以 `!important` 覆盖了图片卡片圆角。
- **修复**：移除照片背景对用户气泡的覆盖，单聊和群聊分别保留无背景时的默认样式；背景预览与选图按钮从通用胶囊规则中豁免，统一使用 14px 圆角矩形。
- **回归**：真实 Electron UI 测试通过界面切换浅色/深色主题及海崖/星夜背景，比较有无背景时的用户气泡配色、阴影和模糊；单聊检查文字对比度至少 4.5:1，并检查两类图片卡片不是胶囊。

## 2026-10-17 · CLI Bot 的判断调用把 CLI 模型名发给 Provider

- **症状**：给本地 CLI Bot 配置判断用 Provider 后，群聊判断仍失败（回退成每条都回复）；Provider 收到的是 CLI 的模型名（如 `gpt-5.6-luna`）。
- **根因**：判断与续发都复用 `completeOnce(bot, …)`，而 `resolveModel()` 优先使用 `bot.model`；对 CLI Bot 来说该字段是 CLI 目录里的模型名，和 Provider 的模型命名空间无关。
- **修复**：新增 `completionBot()`：CLI Bot 借用判断用 Provider 时把 `provider_id` 指向该 Provider 并把 `model` 置空，使用 Provider 默认模型；正文仍由 CLI 生成。
- **回归**：`smoke` 断言 `completionBot(cliBot, provider).model === ''`，并覆盖 CLI Bot 经默认 Provider / Jev / CLI 自身三条判断路径。

## 2026-10-17 · CLI Bot 在群里不主动说话（`auto` + Jev 被误判为无判断引擎）

- **症状**：本地 CLI Bot 在群聊里只回 @提及，即使已经配置了 TypeSafe Jev；设定页也不说明原因。
- **根因**：`hasResponseDecisionEngine()` 只在策略显式为 `jev` 时认 Jev，而默认策略是 `auto`；`auto` 在 `decideResponse()` 里同样会走 Jev，于是「已配置 Jev 的 CLI Bot」被提前判成没有判断引擎，落入只响应 @提及的分支。
- **修复**：判断引擎按真实策略解析——有判断用 Provider 即可；否则 `auto` / `jev` 且 Jev 已配置也算可用，只有 `llm` 明确要求 Provider。设定页在缺少判断引擎时于「判断用 Provider」行标注「群聊里只会被 @ 唤醒」，选中 Provider 后即时恢复。
- **回归**：`smoke` 在 Jev 已配置的环境下覆盖 `llm` 无 Provider（静默且不启动 CLI）、@提及强制发言、`auto` + Jev 正常参与；`test:ui` 覆盖说明行出现与选中 Provider 后消失。

## 2026-10-17 · 判断用 Provider 接管了 CLI Bot 的正文

- **症状**：给本地 CLI Bot 选中判断用 Provider 后，它的回复改由该 Provider 生成，CLI 完全没被调用（测试里表现为假 CLI 调用数为 0、正文变成 mock 文本）。
- **根因**：`runAgent` 先判断 `isMockBot()`（按 `provider_id` 的 Provider 类型），再判断 `isCliBot()`；把 mock Provider 设为判断用时，mock 分支抢在 CLI 之前。
- **修复**：分发顺序改为 CLI 后端优先；判断用 Provider 只参与「是否发言 / 是否续发」的 completion，不接管正文。
- **回归**：`smoke` 给 CLI Bot 配置 mock 判断用 Provider，断言正文仍来自假 CLI 且调用模型正确。

## 2026-10-17 · CLI 模型选择器列出账号不支持的模型

- **症状**：用户从下拉框选择 `gpt-6-luna` 后，Codex CLI 返回 ChatGPT account 不支持该模型的 400 错误，气泡直接展示 JSON。
- **根因**：选择器使用从产品文档取来的固定候选，未查询用户本机 CLI；原有假 CLI 对任意模型均成功，测试只能证明参数保存/传递，不能发现不支持模型。该机的 CLI 0.149.0 实际目录返回 `gpt-5.6-sol` / `gpt-5.6-terra` / `gpt-5.6-luna`。
- **修复**：新建/编辑统一通过 CLI 的 `model/list` 读取目录，保留默认与自定义入口，失败不填入静态候选；已保存模型不在目录时提示并允许用户主动换成目录推荐模型。目录可能有缓存，不声称等同权限检查。运行时将明确的模型不支持错误转换成中文修复建议，不自动换模型或重试。
- **回归**：`smoke` 覆盖分页/去重/隐藏模型、目录错误/空响应/异常分页、不支持模型的中文错误和原配置保留；`test:ui` 覆盖目录候选、刷新、已保存无效模型提示、主动换模型后重试成功。真机只读取模型元数据，未发送聊天或发起付费推理。

## 2026-10-17 · Bot 模型页 CLI 路径与权限修改未落库

- **症状**：已有 CLI Bot 在模型页修改可执行文件或文件权限后，界面和重载后的配置仍是旧值。
- **根因**：共享表单回调使用 `cliPath` / `cliAccess`，模型页将其直接作为 `BotInput` patch 传入；主进程只识别 `cli_path` / `cli_access`，忽略了这两个字段。
- **修复**：模型页将表单字段映射到存储契约；CLI 模型也通过共用选择器提交到 `model`，切换运行方式时清空不兼容的旧模型。
- **回归**：`test:ui` 修改路径、权限与自定义模型后检查 IPC 返回记录及重载回显，并验证创建时选定的模型传入假 CLI 首次和续接调用。

## 2026-10-17 · 本地 CLI 续接时未传模型导致第二轮失败

- **症状**：本地 Codex Bot 第一轮回复正常，第二轮直接失败，气泡显示 `The 'gpt-6.1-sol' model is not supported when using Codex with a ChatGPT account.`
- **根因**：`codex exec resume` 不带 `-m` 时会回退 CLI 自己的默认模型（该账号为 `gpt-6.1-sol`），而会话是用 `gpt-5.6-sol` 建立的；该账号不支持默认模型，整轮 400。真机复现：新建调用带 `-m` 成功，续接不带给 400，续接补上 `-m` 立即成功并正确回忆上一轮内容。假 CLI 只按实现假设输出，无法发现这一类"CLI 自身默认值参与行为"的问题。
- **修复**：新建与续接都下发 `-m`/`--model`（取 Bot 的 `model` 字段，为空时才用 CLI 默认）；模型纳入 `cliFingerprint`，修改模型即重建会话，避免续接模型与建会话不一致。
- **回归**：`smoke` 断言两轮调用都携带 Bot 模型、修改模型后重建会话并带新模型；SPEC §5.4 记录该约束。

## 2026-10-17 · 多模态回归取错请求而失败

- **症状**：`npm run test:multimodal` 在「继续看看之前的图片」一步断言模型请求应包含 4 张图，实际为 0；同一次运行的前三个子用例正常。
- **根因**：用例用该会话最后一个 `/v1/chat/completions` 请求做断言，而「自然追问」会在主回复之后追加一次轻量 completion（约 180 Token、按设计不含图片），使最后一个请求不再指向主回复。产品行为正确：同一批请求中包含 4 张图的主回复请求确实存在。`smoke`、`test:context`、`test:extensions` 都会先关闭 `natural_follow_up`，该用例漏了这一步。
- **修复**：用例创建会话后设置 `natural_follow_up='0'`，与其他回归保持一致，断言重新指向主回复请求。
- **回归**：`test:multimodal` 全部子用例恢复通过；后续新增「断言最后一次模型请求」的用例同样需要先关闭自然追问，或显式排除 `<<...>>` 内部判断调用。

## 2026-09-20 · 推理耗尽输出预算后生成空白消息

- **症状**：群聊连续出现多个空白 Bot 气泡，消息被标记为完成；部分成员长时间停留在“正在回复”。用户怀疑输入上下文溢出。
- **根因**：真实观测日志中 227 次 Agent 完成有 24 次空正文，全部为 `stop_reason=length`；最近请求输入约 7.8k–12.5k Token，远低于 128k 上下文，但 DeepSeek 实验模型将 4096/9096 输出 Token 全部用于 reasoning，未生成可见正文。运行时只检查 Provider error，没有拒绝 `length + 空正文`，因此错误调用了完成回调。32 Token 的群聊判断也会被推理耗尽。
- **修复**：主 Agent 遇到空正文时按停止原因标记 `output_limit` 或 `empty_response`，消息进入失败状态并可靠结束回复指示；已有部分正文时继续保留。群聊和续发的轻量 LLM 判断关闭推理。Bot 默认策略改为自动，在 TypeSafe Jev 已配置时优先 Jev，失败仍回退 LLM。观测事件增加上下文窗口/占比、输出预算占比、推理占比和可见字符数。
- **回归**：`test:context` 用 loopback Provider 模拟 reasoning-only + length，断言不再生成 `done` 空消息、错误可见且 Debug 报告包含 `output_limit` 和预算字段；`smoke` 验证自动策略优先 Jev且低置信度回退；`typecheck`、`test:ui` 覆盖共享契约和策略选择 UI。

## 2026-09-15 · Debug 分析失败只显示 provider_error

- **症状**：原回复已经正常结束，但 Debug 分析失败，界面只显示层叠的 IPC 错误和 `provider_error`，无法区分是哪次调用、哪个模型以及失败阶段。
- **根因**：独立诊断固定使用 2048 输出预算和 45 秒超时；completion 仅返回正文，丢失停止原因和用量，空正文也被归为通用 Provider 错误。分析调用本身没有关联日志。截图不足以确定真实服务的失败原因，不能将这些代码缺陷等同于已证实的上游根因。
- **修复**：沿用诊断 Bot 参数，超时放宽到 120 秒；识别仅推理/空正文与 length 截断，分类显示网络、鉴权、参数等错误。每次分析记录独立编号及脱敏元数据，和源回复事件区分；UI 去掉 IPC 包装并显示诊断模型与预算。不自动重试付费调用、不泄露原始错误。
- **回归**：`test:context` 使用临时 profile 和 loopback 服务，覆盖空正文、推理耗尽预算、部分正文截断、鉴权失败、取消后重试、参数传递、日志关联及错误脱敏；`typecheck` / `smoke` 验证共享运行时调用未回归。

## 2026-09-15 · Debug 报告漏掉调度器与内部模型调用

- **症状**：单条 Bot 回复报告只有主 Agent 执行片段；定时器是否触发、群聊为何跳过 Bot、续发判断失败等关键过程无法与回复放在一起查看。工具同名多次调用也不易区分。
- **根因**：调度器没有写本地观测事件；非流式 `completeOnce` 只有诊断分析自行记录；续发/群聊子调用未沿用同一轮标识。Debug 仅按消息 ID 过滤，因此全局日志里已有的续发候选事件实际无法进入对应报告。
- **修复**：普通用户轮次增加匿名 trace ID，串联群聊决策、内部 completion、续发、摘要和 Bot 回复；定时任务用独立 trace ID，并记录计划恢复、触发来源、跳过原因、结束状态、耗时及下次运行时间。非流式模型调用记录阶段、HTTP 状态、用量与错误分类；工具日志增加序号和错误分类。Debug 按原消息 ID 找到 trace 后合并同轮事件。仍不记录 prompt、任务内容、工具输入输出或原始异常。
- **回归**：`npm run smoke` 在临时 profile 断言群聊决策及手动定时任务的触发、Agent 执行和完成事件出现在同一份消息诊断报告，并确认任务正文不入日志；`npm run test:context` 验证续发事件可由报告读取、ID 匿名化和工具调用序号。`npm run typecheck` 覆盖 IPC 外部类型不变。

## 2026-09-15 · 引用样式与卡住回复的定位入口

- **症状**：引用图标形状不自然，点击后直接向输入正文插入 `>` 标记；长草稿出现突出滚动条。回复停在准备或工具阶段时，用户难以关联本地日志定位原因。
- **根因**：引用使用手绘图标和纯文本追加，没有独立草稿结构；运行日志主要按会话/Bot 记录，缺少消息维度关联和可用的诊断入口。
- **修复**：换用标准 Quote 图标、独立持久引用块和隐藏滚动条。每条 Bot 回复新增 Bug 复制入口，普通/定时 Agent 执行事件关联消息 ID；Debug 页加载脱敏元数据并支持独立 LLM 分析、超时及取消。日志默认仍关闭，缺失历史明确标注，不推断没有日志就没有执行。
- **回归**：`test:ui` 验证引用恢复、取消、发送、长输入滚动和生成中 Bug 按钮；`test:context` 验证文件工具事件精确关联、隐私字段、损坏日志行、非法/缺失标识、日志开关和 loopback 模型诊断页面。取消分析须检查 AbortSignal，避免底层取消返回空文本时误报成功，并验证取消后重试。

## 2026-09-15 · Agent 未写文件却声称已交付

- **症状**：用户要求生成、保存或修改工作区文件时，Agent 偶尔只用文本描述结果，却说文件已经写入，聊天中没有可靠交付卡，工作区也找不到对应产物。
- **根因**：运行时虽已提供文件工具与交付卡，但工具提示只笼统要求“不要伪造”，没有把“完成性措辞”绑定到本轮 `workspace_write` / `workspace_edit` 的成功结果；模型容易把计划性回答误说成已完成。
- **修复**：工具提示明确规定：只有收到本轮写入或编辑成功结果，才可声称文件已写入、已保存、已生成或给出产物路径；无成功结果必须说明尚未完成或失败原因。交付 UI 继续只以结构化工具结果生成卡片，不解析正文。
- **回归**：`npm run test:context` 的真实 Agent 工具循环断言写入、编辑和交付卡均来自工具结果；`npm run smoke` 覆盖默认模型预算。

## 2026-09-15 · 定时任务结束后会话一直显示回复中

- **症状**：定时任务触发、完成或失败后，聊天界面仍显示「正在思考是否回复」或「正在回复」，发送状态无法恢复；视觉上像后台任务与正常对话续发冲突。
- **根因**：定时任务只广播了 `message-start` 和 `message-done`，渲染层据此将会话设为生成中，却没有能与普通 `generation-state` 区分的后台任务结束信号。普通轮次和定时轮次共用单一布尔状态，无法安全收尾。
- **修复**：新增成对的 `scheduled-task-state` 事件；渲染层分别记录用户轮次、定时任务 ID 集合和流式消息，只有三者都结束才退出生成状态。定时任务不触发自然追问或群聊续发，只投递自己的最终消息。
- **回归**：`npm run smoke` 断言手动执行任务的开始/结束状态事件成对出现；`npm run test:ui` 验证定时任务完成后会话不再保持生成中。

## 2026-09-10 · 顺序群聊思考时无法补充消息

- **症状**：群聊使用默认顺序回复时，只要有 Bot 在思考，Composer 就只显示停止按钮，用户只能等整轮结束。
- **根因**：渲染层和 IPC 只对 `reply_mode='active'` 放开生成期间发送，编排器的判断修订会话也只在主动模式创建。
- **修复**：所有进行中的群聊共用修订号、强制提及集合和判断 AbortController。新消息立即落库，取消尚未完成的判断；顺序模式当前成员和主动模式全体成员都使用最新上下文重试。
- **回归**：`npm run smoke` 验证顺序模式的补充消息立即落库、当前成员重新进入思考并在回复中使用新内容；`npm run test:ui` 验证群聊流式输出时发送和停止按钮同时可用。

## 2026-09-10 · LaTeX 公式显示为原始文本

- **症状**：Bot 回复中的 `$E=mc^2$`、`$$...$$` 和矩阵等公式以带反斜杠的原始文本显示，无法阅读。
- **根因**：Markdown 渲染链只启用了 GFM 和代码高亮，没有把数学语法解析为节点，也没有加载 KaTeX 样式。
- **修复**：接入 `remark-math` 与 `rehype-katex`，启用单美元行内公式和双美元块级公式；兼容同一行的 `$$...$$`、`\[...\]` 写法；KaTeX 遇到无效公式时保留错误文本，不中断整条消息；块级公式独立横向滚动。
- **回归**：`npm run test:ui` 的 Markdown fixture 同时断言行内 `.katex` 和块级 `.katex-display` 可见，并继续验证表格、代码高亮、任务列表和不安全链接过滤。

## 2026-09-10 · Bot 用文本冒充已完成跨 Bot 私聊

- **症状**：用户要求 Kimi Bot 咨询另一位 Bot 时，回复声称“已经问过”并引用对方回答，但会话中没有私聊卡片，也没有实际工具调用。
- **根因**：运行时已向模型提供 agent_private_chat，但旧系统提示仅说明“可以”使用，没有规定明确咨询请求必须调用，也没有禁止在缺少工具结果时模拟另一位 Bot 的回复。模型以普通文本结束后，应用无法把其陈述当作真实工具执行。
- **修复**：系统提示新增跨 Bot 咨询真实性约束：明确请求必须先 list_bots 再 agent_private_chat，只有收到本轮工具结果才能声称完成或转述回复；失败、不可用及目标不存在时必须如实说明。工具装配提示同步强调该规则。
- **回归**：`npm run smoke` 断言运行时系统提示同时包含强制调用、结果前置、禁止伪造和执行事实核验约束。

## 2026-09-10 · LM Studio 无法识别本轮 user query

- **症状**：用户在单聊发送“继续呢”等正常消息后，LM Studio/Qwen 返回 Jinja template 错误 `No user query found in messages`。
- **根因**：数据库和 pi 历史中存在 user 消息，但运行时把它随历史预填给新 Agent，再调用 `agent.continue()`；部分 LM Studio 模板只把本轮显式 prompt 识别为 user query，无法兼容这种 continuation 启动方式。
- **修复**：Agent 初始历史只保留到最新输入之前，最新 user/toolResult 消息改由 `agent.prompt(message)` 显式提交；新增默认关闭的隐私安全本地观测，记录历史与最终 payload 的角色摘要、续发结果及错误分类。
- **回归**：`npm run test:context` 的 OpenAI-compatible fixture 断言首个真实 Agent payload 最后一条为 user，并验证日志包含 `payload_last_role=user`，且不含已知聊天正文。

## 2026-09-10 · 私聊自然追问复述并暴露分段机制

- **症状**：Bot 已在主回复中完整回答，随后却从开头复述，还可能说“下一条来了”“重新来”等暴露内部调度的话。
- **根因**：旧流程先用一次 completion 判断 `REPLY|SKIP`，再对以 assistant 消息结尾的历史调用 `agent.continue()` 生成正文；判断与生成相互独立，且违反运行时要求历史最后一条为 user 消息的约定。发送前也没有内容校验。
- **修复**：较长主回复先生成一个自然完整的语义段；续发改为一次轻量 completion 同时决定并起草候选，默认 `SKIP`。候选只有在能推进未完成的新内容、遗漏重要信息或需要明确回答时才允许发送，并在落库前检查长度、近期回复长片段重复和调度元话术。
- **回归**：`npm run smoke` 验证较长回答按三个不重复语义段依次发送、有价值候选只发一次并及时停止、两个不同承接点最多发送两条、包含“下一条来了”的候选被拦截，以及关闭开关后只保留主回复。

## 2026-09-10 · Agent 看似无法调用工具

- **症状**：Bot 面对文件读写、网页原文或最新信息任务时，容易只给文本建议，缺少可验证的实际操作。
- **根因**：pi-agent-core 的 ReAct 循环已接通，但工具直接在 `agentRuntime.ts` 内零散拼装；只有基础文件读/写/列表，没有网页工具、精确编辑、分页读取和明确的模型工具指引。
- **修复**：新增单一能力装配层，将工作区、只读网页与应用工具按会话权限组合；网络层由 Electron 注入 Chromium `net.fetch` adapter，继承系统代理并兼容 Fake-IP，动态页再自动回退到隐藏沙箱 BrowserWindow 执行 JavaScript；文件层加入 realpath 防逃逸。
- **回归**：`npm run test:context` 通过本地 OpenAI-compatible fixture 执行真实 tool-call/result 循环，验证写入→精确编辑→列表→分页读取和普通/私聊工具集权限；同时用 Chromium Fake-IP 域名映射与本地 HTTP 代理提供只能由 JavaScript 写入的 DOM 标记，断言渲染后内容经工具回灌模型。

## 2026-09-10：Bot 私聊内容无法跨会话回忆

- 症状：猛男转达给 ds 的信息，在用户随后与 ds 的单聊里无法召回。
- 根因：agent_private_messages 仅作 UI 记录，不参与记忆写入；普通聊天依赖十条阈值异步提取，且只注入最近三十条记忆。
- 修复：DAO 在消息完成时向实际双方/成员写入带来源的即时记忆，所有生成入口按话题和人物检索；增加层级、证据归纳、淘汰和旧私聊补入。
- 回归：smoke 覆盖双方归属、跨会话检索、失败/停止、归纳证据、纠正、TTL/容量、删除和重启迁移；context Electron 回归覆盖真实私聊完成后的双向记忆与接收方后续模型输入、分层 UI 与删除。

## 2026-09-10：短时记忆被原文填充，没有实时摘要

- 症状：记忆面板主要显示完整原文；短时记忆没有反映当前话题、结论和待办。
- 根因：第一阶段修复虽把原文移到 evidence 层，但短时摘要仍以整个场景为唯一主键，且质量校验只拒绝与单条原文完全相等；模型给原文增加少量连接词、截取或拼接大段原文时仍会被标成摘要。
- 修复：同一场景按最多 10 条、首尾不超过 15 分钟切成非重叠短时窗口，段内持续更新同一摘要，越界开启新摘要；场景摘要继续维护跨窗口脉络。新增近似摘抄检测、证据范围校验和一次自动重试，并在启动、刷新或后续归纳时清理已有的不合格短时/场景摘要；启动清理后提示手动刷新，不静默调用模型。
- 回归：smoke 验证第 11 条消息与 15 分钟边界会创建新窗口、窗口互不重叠、摘要近似原文会被拒绝、场景更新和持久游标；context Electron 验证真实摘要请求、分层筛选、实时刷新和失败可见。
