# Cindy 近期合入能力与 Covan 借鉴报告

本报告的结论是：Covan 不需要复制 Cindy 的移动端、远程桌面或个人构建产品线；它已经具备定时任务、隐私安全诊断、Bot 级工作区和 MCP Skills 装配等扎实底座。最值得吸收的是 Cindy 在“长期 Agent 的状态归属”“对话级工作区”“Provider 的可信接入与透明度”上的产品和工程模式。建议把这些模式拆成小步演进，而不是引入 Cindy 的完整概念体系。

## 建议借鉴的设计与落地方式

### 1 对话级工作区

**现状。** Covan 的工作区根路径为 `workspaces/<botId>/`。这保证了 Bot 间隔离，但同一个 Bot 的多个私聊或群聊会共享产物和上下文文件。Cindy 最近将对话工作区做成独立、可恢复且可配置的资源，说明工作区一旦进入真实使用，目录失效、迁移和重启恢复会迅速成为核心边界。

**建议。** 保留 `workspaces/<botId>/` 作为 Bot 私有长期资料根；新增 `workspaces/<botId>/chats/<chatId>/` 作为默认的会话交付目录。工具上下文明确标明两种作用域，默认写入会话目录，只有经过显式工具参数或用户操作才读取 Bot 共享目录。

**验收要点。** 旧工作区不移动、不丢失；新会话文件不会出现在其他会话；删除或隐藏会话不自动删除产物；已失效目录的恢复只提供诊断和重新选择入口；路径、符号链接与预览协议回归覆盖两层目录。

### 2 长期 Bot 与临时运行的状态分层

**现状。** Covan 已将 Bot、聊天、记忆、定时任务分表，但应用启动时会把所有 `streaming` 消息标为 `stopped`，且明确不会自动恢复网络请求。这是安全的默认策略。Cindy 的可借鉴点是把“永久档案”与“可更换、可失败、可重新建立的运行会话”分开，并让用户看到稳定的终态和恢复入口。

**建议。** 增加通用 `agent_runs` 记录，保存 `chat_id`、`bot_id`、触发类型、运行阶段、开始/结束时间、恢复资格、归一化失败码和可安全展示的摘要。保留现有“不自动续发”原则：重启后把运行标为 `interrupted`；对不具副作用或可显式确认重试的工作，提供“以相同输入重新开始”而不是“恢复 HTTP 流”。

**先后顺序。** 先让定时任务、Agent 私聊和普通回复共用状态模型，再考虑真正的后台队列。这样能够复用已有 trace、观测和取消逻辑，也避免引入一套平行生命周期。

### 3 Provider 连接可信接入与透明度

**现状。** Covan 目前的 Provider 数据模型只表达名称、类型、API Key、Base URL 和默认模型；路线图已明确 API Key 仍是 SQLite 明文，密钥迁移为 P0。Cindy 的 Provider 导入、来源标签和订阅余量能改善上手和决策，但“从深链接带入密钥”会扩大泄露、重放和钓鱼链接风险。

**建议。**

1. 先做 `safeStorage` 加密、旧值迁移、无法加密时的拒绝保存和回滚测试。
2. 引入“连接”层，而非直接让模型绑定 Provider：记录来源类型（手工、导入、本地）、能力、上次验证时间和显示名称；密钥永不回传到 renderer。
3. 在模型选择器显示来源、可用能力和“数据更新时间”；群聊开始前显示预估调用成员与 token 上限。
4. 最后才做导入。导入只产生待审核草稿，展示将要写入的域名、模型和权限；默认不支持 URL 直接携带长期密钥，不允许重定向，不在日志、历史或剪贴板持久化密钥。

### 4 从本地扩展管理到渐进发现

**现状。** Covan 已明确暂不提供 OAuth、MCP resources/prompts 和在线市场；这与当前以本地优先和最小权限为目标是一致的。Cindy 的参考价值在“需要时才发现、安装和装配”，而不是让 Agent 自由下载任意插件。

**建议。** 将在线目录列为 P2：先从只读、审核过的静态清单开始，清单项展示来源、版本、内容哈希、所需 MCP 传输、网络域名和运行权限。安装必须经过用户确认，安装后仍默认未装配到任何 Bot。Agent 只可提出候选和解释用途，不能绕过确认安装或扩大权限。

### 5 会话管理与成本可见性

**现状。** Covan 路线图已列出全文搜索与会话归档、群聊预算和 Provider 模型摘要。Cindy 本轮记住最近入口、模型来源和额度的改动，说明这些不是“设置页装饰”，而是高频任务流的一部分。

**建议。** 按已有路线图推进：先做真正的归档和 SQLite FTS，再保存最近打开的会话；群聊发送前展示参与 Bot、模型和每轮上限，完成后展示实际 token 摘要。价格和订阅额度仅在服务提供可靠来源时显示，缺失时宁可写“不可用”，不要估算成事实。

### 6 在现有脱敏诊断上增加工作区状态摘要

**现状。** Cindy 将工作目录故障纳入安全诊断。Covan 已有更通用的 trace 和字段白名单，但没有面向工作区的状态投影。

**建议。** 在诊断报告中增加经过脱敏的工作区状态：目录可用性、文件数量分桶、最近一次安全校验结果、是否发生符号链接拒绝和错误类别。不要记录绝对路径、文件名、文件内容或原始系统错误。该项适合作为 P2 的可靠性增强。

## 不建议当前引入的方向

| 方向 | 不建议的原因 | 重新评估条件 |
| --- | --- | --- |
| 远程桌面、跨设备控制和移动端原生改造 | 需要摄像/输入/剪贴板权限、端到端安全模型和多端运维；与 Covan 当前桌面多 Bot 核心目标相距较远。 | 用户明确需要跨设备控制，且先完成权限、审计和端侧安全设计。 |
| Cindy Make 式的个人构建工作流 | 它服务于 Cindy 自身分支、源码准备和发行过程，不是通用的聊天产品能力。 | Covan 将来要内置“执行代码项目并管理 worktree”的独立产品线。 |
| 套餐购买和余额展示 | Covan 目前更需要可信的用量摘要与预算控制；支付、订阅和账务会带来额外合规与支持负担。 | 有明确商业化方案和可信计费来源。 |
| 不受控的在线插件市场或自动安装 | 当前 MCP 子进程具有用户权限，自动安装会把供应链风险放大。 | 建立签名、哈希、权限审核、撤销机制和用户确认链路之后。 |

## 推荐实施顺序

1. **先完成既有 P0。** Provider 密钥 `safeStorage` migration 和工具活动可见化优先级不变；这两个能力是引入连接导入、通用运行记录和目录发现之前的信任基础。
2. **再做会话工作区和运行记录。** 二者共享“稳定资源归属、临时运行可中断”的模型；先完成数据迁移、取消与重启后的可解释状态，再补 UI。
3. **补管理闭环。** 归档与搜索、最近会话、群聊预算与 Provider 来源一起提供高频决策信息。
4. **最后探索扩展目录。** 仅以只读候选目录和明确确认流试点；以安装成功率、权限拒绝率和安全审计结果决定是否扩大范围。

这条路径保留了 Covan 的本地优先、多 Bot 和安全边界，同时吸收 Cindy 在复杂状态管理上的成熟做法，而不会把产品拖入跨端控制、构建发行或商业计费等不相干的高成本方向。
