# PRD — Covan 产品需求文档

> 版本：v1.0 · 与 SPEC.md 保持一致；SPEC.md 为技术接口与模块边界的单一事实来源，本文档负责产品侧的目标、用户、需求与验收标准。

## 1. 背景与机会

大语言模型正在从「单一聊天助手」演化为两个快速增长的使用场景：

**场景一：多智能体协作（Multi-Agent Collaboration）。** 独立开发者与小团队越来越倾向于用多个有不同人设与专长的 AI 角色（后端工程师、架构师、Code Reviewer、测试员、产品经理、设计师）组成一个「虚拟团队」，围绕同一个问题展开讨论。单一聊天窗口无法表达「角色之间的对话与分工」，而现有协作工具要么绑定特定 SaaS 账号体系、要么数据上云，隐私与成本都不可控。市场缺少一个**本地优先、自带人设模板、由协调者主持讨论**的多 Bot 群聊桌面应用。

**场景二：AI 情感陪伴（AI Companion）。** 以 Grok Bot 为代表的产品证明了「有持久人设、有记忆、语气亲昵」的虚拟伴侣拥有真实且旺盛的个人用户需求。陪伴体验的关键不在于模型本身，而在于**人设的持续性**与**记忆的累积**——用户希望自己的喜好、纪念日、生活细节被长期记住，而网页会话式的 AI 无法提供这种连续性。

Covan 的机会在于：**同一套「Bot（人设 + 记忆 + 工作区 + 模型配置）」内核同时服务这两个场景**——工作伙伴与虚拟伴侣只是人设模板的不同实例。配合本地 SQLite 存储与用户自备 API key（BYOK），Covan 提供隐私可控、模型可换、可离线管理资产的多 Bot 桌面体验。

## 2. 产品目标与成功指标

### 2.1 产品目标

- G1：让用户在 5 分钟内完成「配置 provider → 创建 Bot → 发起对话」的闭环。
- G2：让用户可以组建 2 个以上 Bot 的群聊，由协调者 Bot 主持一场有秩序、有分工的多轮讨论。
- G3：让 Bot 具备跨会话的长期记忆，且用户可查看、手动增删。
- G4：所有数据本地存储，无遥测、无账号体系，用户对自己的数据与密钥拥有完全控制权。
- G5：虚拟伴侣场景开箱即用（内置「小美女」人设模板），陪伴体验流畅、可被记忆强化。

### 2.2 成功指标

| 指标 | 目标 |
| --- | --- |
| 首次启动到首次收到 Bot 回复的时长 | ≤ 5 分钟（含 provider 配置） |
| 群聊讨论完成率（用户发起群聊消息后，全部计划发言人成功产出回复的比例） | ≥ 95%（排除用户主动停止） |
| 记忆留存感知 | 同一 Bot 隔日对话能引用 ≥ 1 条历史记忆中的事实/偏好 |
| 可中断性 | 停止操作后 1 秒内流式输出停止，消息状态正确标记为 stopped |
| 崩溃与数据损坏 | 0 起数据库损坏事件；任何生成失败不丢失已落库消息 |
| 冒烟测试 | `npm run smoke` 全绿（mock provider：建 bot→建群→发消息→收回复→记忆写入） |

## 3. 目标用户与 Persona

### Persona A：独立开发者「阿澈」

- 28 岁，全栈独立开发者，一人维护两个 SaaS 副业项目。
- 痛点：身边没有可讨论技术方案的同事；和单个 AI 聊天得到的是「一种意见」，想要「一场争论」；不想让代码与想法留在别人的云端。
- 诉求：把「高级全栈 + 架构师 + Reviewer + 测试员」拉进一个群，抛出设计问题，看它们依次发言、互相补充；讨论产物（方案、代码片段）落进 Bot 的工作区文件。
- 关键场景：多 Bot 群聊 + 协调者主持 + 工作区读写。

### Persona B：小团队技术负责人「林姐」

- 35 岁，8 人创业团队 tech lead，公司有自建 OpenAI 兼容网关（openai-compatible base_url）。
- 痛点：团队评审资源紧张，希望在正式评审前先用 AI「模拟评审」过滤低级问题；公司网关的 key 不能上传到任何第三方平台。
- 诉求：自定义 provider（openai-compatible）、按 Bot 配置不同模型与温度、本地存储密钥。
- 关键场景：provider 管理 + Bot 级模型配置 + 本地优先。

### Persona C：需要情感陪伴的个人用户「小北」

- 24 岁，异地工作，独居，睡前喜欢有人聊天。
- 痛点：普通 AI 助手语气疏离、聊完就忘；想要一个「记得我口味、记得我生日、会夸我」的存在。
- 诉求：选一个现成的虚拟女友人设（小美女），日常闲聊；Bot 主动记住喜好与纪念日；界面温暖、操作简单。
- 关键场景：人设模板 + 单聊 + 自动记忆 + 暗色模式夜间使用。

## 5. 功能需求（FR）

> 每个 FR 给出优先级与 Given-When-Then 验收标准。模块划分与 SPEC.md §2 一致。

### 5.1 Bot 管理

**FR-BOT-01 创建 Bot（P0）**
- Given 用户已打开应用，When 点击侧边栏「+」→「新建 Bot」（快捷键 ⌘1）并填写名称、选择人设模板/provider/模型后确认，Then 系统创建 Bot 记录、自动创建其工作区目录 `workspaces/<botId>/`，Bot 出现在侧边栏列表中。

**FR-BOT-02 人设模板（P0）**
- Given 新建 Bot 对话框打开，When 用户在人设模板下拉中选择「虚拟女友·小美女」，Then system prompt 编辑区自动填入对应模板内容，且用户可继续修改；选择「空白自定义」则留空。

**FR-BOT-03 编辑 Bot（P0）**
- Given 用户在单聊中打开右侧 BotSettingsPanel，When 修改名称/标签/描述/人设/模型/温度/通知开关，Then 变更即时保存并广播 `bot-updated` 事件，后续对话立即生效。

**FR-BOT-04 删除 Bot（P1）**
- Given 某 Bot 存在历史消息，When 用户删除该 Bot，Then Bot 及其记忆、工作区关联被移除，但 messages 表中其历史消息保留并正常展示（头像降级为占位样式）。

**FR-BOT-05 头像（P1）**
- Given Bot 设置面板，When 用户点击更换头像并选择本地图片，Then 图片拷贝至 `avatars/` 并更新 Bot 头像；图像生成头像为可选实现，失败时返回空并静默降级为 emoji 头像。

**FR-BOT-06 置顶与排序（P1）**
- Given 侧边栏，When 用户置顶某 Bot，Then 其头像出现在置顶区横排并显示在线绿点，按 sort_order 排序。

### 5.2 会话与消息

**FR-MSG-01 发起单聊（P0）**
- Given 侧边栏存在 Bot，When 用户点击 Bot 或调用 createDm，Then 创建（或复用）与该 Bot 的 dm 会话并进入对话视图。

**FR-MSG-02 发送消息与流式回复（P0）**
- Given 任意会话，When 用户输入文本并按 Enter 发送，Then 用户消息立即落库并显示，Bot 回复以流式 delta 逐步渲染（打字光标可见），完成后消息状态置为 done。

**FR-MSG-03 消息持久化与分页（P0）**
- Given 某会话存在大量历史消息，When 用户打开会话或向上滚动，Then listMessages 按 before/limit 分页加载，消息顺序与状态（streaming/done/error/stopped）正确还原。

**FR-MSG-04 停止生成（P0）**
- Given Bot 正在流式输出，When 用户点击停止按钮，Then 该会话所有进行中的生成被 abort，消息状态标记为 stopped，已输出内容保留。

**FR-MSG-05 错误内联与重试（P0）**
- Given 生成因 key 失效/超时/限流失败，When 错误发生，Then 气泡内联显示错误信息与重试入口；点击重试后以相同上下文重新发起生成。

**FR-MSG-06 @ 提及（P0）**
- Given 群聊 Composer，When 用户通过 @ 按钮选择成员并发送，Then 消息 mentions 字段记录 botId 列表，被提及 Bot 在编排中强制加入发言列表首位。

**FR-MSG-07 未读与已读（P1）**
- Given 非当前会话收到新消息，When 消息落库，Then 会话列表项显示未读蓝点；用户进入该会话时 markRead 清除未读。

### 5.3 群聊编排

**FR-GRP-01 创建群聊（P0）**
- Given 至少存在 2 个 Bot，When 用户通过「+」→「创建群聊」（⌘2）填写群名、勾选成员、可选指定协调者 Bot，Then 创建 group 会话并写入 chat_members（协调者 role='coordinator'）。

**FR-GRP-02 协调者主持讨论（P0）**
- Given 群配置了协调者，When 用户发送群消息，Then 系统构建最近 30 条 transcript 交给协调者，协调者仅输出 JSON 决策（speak 列表 + note），系统写入 note 系统消息后按 speak 列表串行调度各 Bot 发言。

**FR-GRP-03 无协调者兜底（P0）**
- Given 群未配置协调者，When 用户发送消息，Then 被 @ 的 Bot 发言；无 @ 时全体成员按 sort_order 依次发言，最多 5 人。

**FR-GRP-04 决策解析失败兜底（P0）**
- Given 协调者输出无法解析为合法 JSON，When 解析失败，Then 系统降级为「所有被 @ 的 Bot + 协调者自己」发言，不中断本轮讨论。

**FR-GRP-05 群聊发言上下文（P0）**
- Given 某 Bot 被调度发言，When 构建其 system prompt，Then 注入其人设 + 长期记忆 + 群聊上下文指令（所在群名、其他成员、口语化简短回复、不复述别人），协调者 hint 以 `(协调者提示: …)` 前缀拼入用户消息。

**FR-GRP-06 群聊成本控制（P0）**
- Given 一轮群聊调度，When 协调者返回的发言列表过长，Then 系统按最大发言数上限截断（详见 ARCHITECTURE.md §11），防止成本失控。

### 5.4 记忆系统

**FR-MEM-01 记忆注入（P0）**
- Given 某 Bot 存在记忆，When 发起任意一次该 Bot 的生成，Then 最近 30 条记忆以 `## 你的长期记忆` 列表格式注入 system prompt。

**FR-MEM-02 自动提取（P0）**
- Given 某会话累计产生 10 条新消息，When 触发后台提取，Then 系统用该 Bot 自己的 provider/model 做非流式调用，从最近对话提取事实/偏好/约定/重要事件，与现有记忆去重（包含关系即跳过）后入库；提取失败静默，不影响主流程。

**FR-MEM-03 手动管理（P0）**
- Given Memory 标签页，When 用户添加或删除一条记忆，Then memories 表即时更新，下一次生成即生效/失效。

**FR-MEM-04 陪伴强化（P0）**
- Given 使用「小美女」模板的 Bot，When 自动提取运行，Then 人设模板中的记忆引导（主动记住喜好、纪念日）使此类信息被优先提取入库。

### 5.5 工作区

**FR-WS-01 独立工作区（P1）**
- Given Bot 创建成功，When 查看文件系统，Then `userData/workspaces/<botId>/` 目录存在；agent 运行时 cwd 限定于该目录。

**FR-WS-02 文件浏览与预览（P1）**
- Given Workspace 标签页，When 用户打开，Then 列出深度 2 的文件树；点击文本文件（≤200KB）可预览内容。

**FR-WS-03 系统打开（P1）**
- Given Workspace 标签页，When 用户点击「在访达中打开」，Then 调用 shell.openPath 打开该 Bot 工作区目录。

**FR-WS-04 Agent 文件工具（P1）**
- Given Bot 正在生成，When 模型调用 workspace_read/workspace_write/workspace_list 工具，Then 操作被限制在其工作区内，任何 `..` 路径逃逸被拒绝。

### 5.6 Provider 与模型

**FR-PRV-01 添加 Provider（P0）**
- Given SettingsModal 的 Provider 管理页，When 用户填写名称、kind（openai/anthropic/google/openrouter/kimi Coding Plan/zhipu/deepseek/openai-compatible）、api_key、base_url（openai-compatible 必填）、默认模型并保存，Then provider 落库并出现在列表，并显示对应 Provider 图标。

**FR-PRV-02 测试连接（P0）**
- Given 已保存的 provider，When 用户点击「测试连接」，Then 系统发起一次最小 completion（ping），返回 ok/error（及可用模型列表，若可得）并展示。

**FR-PRV-03 Bot 级模型覆盖（P0）**
- Given Bot 设置面板，When 用户为 Bot 指定 provider 与模型（留空则用 provider 默认模型）及 temperature、max_tokens，Then 该 Bot 的所有生成使用此配置。

**FR-PRV-04 Mock Provider（P0，可测试性）**
- Given 开发/冒烟环境，When provider kind='mock'，Then 不走真实 LLM，按模板生成流式假回复，`npm run smoke` 依赖其完成端到端验证。

**FR-PRV-05 拉取账号模型（P0）**
- Given Provider 已填写 API Key，When 用户点击「拉取模型」，Then 系统从 Provider 模型接口获取当前账号可用模型，默认模型使用拉取结果中的选择，不依赖写死的旧模型名。

### 5.7 设置

**FR-SET-01 通用设置（P1）**
- Given SettingsModal，When 用户修改外观（跟随系统/浅色/深色）、语言，Then 设置持久化于 settings 表并即时生效。

**FR-SET-02 审核规则（P1）**
- Given 设置中的「自动审核」开关与规则文本，When 开关打开且用户在群聊发消息，Then 规则文本作为自然语言注入协调者决策前的检查环节。

**FR-SET-03 时区（P1）**
- Given 首次运行，When 应用启动，Then 自动检测系统时区并写入设置，供记忆与提示词使用。

### 5.8 主题

**FR-THM-01 浅色默认 + 跟随系统暗色（P1）**
- Given 默认安装，When 系统处于浅色/深色模式，Then 应用以浅色（暖灰 stone 系）默认呈现，或按设置跟随系统切换暗色；用户可手动锁定主题。

## 6. 非功能需求（NFR）

**NFR-01 隐私本地优先（P0）**：所有数据（bots、chats、messages、memories、providers、settings）仅存本地 SQLite；应用无任何网络遥测，除用户配置的 LLM provider 外不发起任何外部请求。

**NFR-02 性能（P0）**：启动到首屏可交互 ≤ 3 秒；流式 delta 事件渲染延迟肉眼无感（逐 token 更新不重排整列表）；消息分页加载每页 ≤ 50 条；数据库启用 WAL 模式避免读写互斥。

**NFR-03 可中断性（P0）**：一切外部调用（LLM 流式、测试连接）均可通过 AbortController 中断；生成中用户可自由切换、浏览其他会话，多会话并发生成互不阻塞。

**NFR-04 错误处理（P0）**：key 无效、超时、限流、网络错误均在消息气泡内联展示并可重试；后台任务（记忆提取、图像头像生成）失败静默降级，绝不弹窗打断用户。

**NFR-05 安全（P0）**：渲染进程启用 contextIsolation、禁用 nodeIntegration，仅通过白名单 IPC 通道访问主进程能力。**API key 以明文存于本地 SQLite——这是 v1 的已知风险与明确取舍**：README 必须显著注明该风险，后续版本规划迁移至 Electron safeStorage 加密存储（见 ARCHITECTURE.md §11）。

**NFR-06 代码质量（P0）**：`tsc --noEmit` 与 `electron-vite build` 通过；交付含冒烟脚本 `npm run smoke`。

### 7.2 核心流程一：首次启动 → 配置 provider → 建 bot → 建群 → 讨论

1. 首次启动，应用初始化本地数据库与工作区根目录，进入空态会话列表，引导用户打开 SettingsModal。
2. 用户在 Provider 管理页新增 provider（如 openai-compatible 公司网关），填写 key 与 base_url，点击「测试连接」看到成功提示。
3. 用户点击「+」→「新建 Bot」，依次创建「高级全栈」「架构设计师」「Code Reviewer」三个 Bot（人设模板自动填充 system prompt，模型走 provider 默认）。
4. 用户点击「+」→「创建群聊」，命名「架构评审组」，勾选三个 Bot，指定「架构设计师」为协调者。
5. 用户在群 Composer 输入：「我打算把订单服务从单体拆出去，@架构设计师 你先给方案。」
6. 协调者输出 JSON 决策（note 以系统胶囊显示：「已安排 3 位成员发言」），架构设计师先发言，其余成员按调度依次补充，全部流式呈现。
7. 讨论结束后后台触发记忆提取；用户可随时打开某 Bot 的工作区查看产出的方案文件。

### 7.3 核心流程二：陪伴场景

1. 用户「新建 Bot」选择「虚拟女友·小美女」模板，命名后进入单聊。
2. 日常闲聊中用户提到「我下周三生日」「我不吃香菜」，消息累计 10 条后后台自动提取，这两条进入 Bot 的长期记忆。
3. 隔日用户再打开会话，Bot 的记忆注入 system prompt，回复中自然提及生日与饮食偏好，用户感到「被记得」。
4. 用户在 Memory 标签页查看已记住的内容，手动补充「最近在准备面试」；也可删除不想被记住的条目。
5. 夜间用户切换深色模式继续聊天；任何回复太长时可随时点停止。

## 8. 边界情况与异常流

| 场景 | 系统行为 |
| --- | --- |
| 未配置任何 provider 即创建 Bot 并发言 | 新建 Bot 对话框允许保存（provider 可空），发送消息时该 Bot 回复以 error 气泡提示「请先配置 provider」，引导跳转设置 |
| provider key 失效 / 被吊销 | 生成失败，气泡内联展示错误与重试入口；测试连接可快速定位是哪个 provider 出问题 |
| 生成过程中用户点击停止 | 该会话所有 AbortController 被 abort，消息状态置 stopped，已输出内容保留；不产生额外系统消息 |
| 协调者输出非 JSON / JSON 结构非法 | 兜底策略：所有被 @ 的 Bot + 协调者自己发言；note 降级为默认系统文案；不中断本轮讨论 |
| 群聊无成员（空群） | 创建群聊时成员数 < 2 给出表单校验提示；存量空群发消息时回复系统消息「群里还没有成员」 |
| Bot 被删除但消息保留 | 历史消息正常展示，发送者显示为已删除占位头像与名称；该 Bot 不再出现在新建群聊成员候选 |
| 记忆提取时 Bot 无可用 provider | 回退到全局默认 provider；仍不可用则本次提取静默跳过 |
| 工作区文件过大或二进制 | 预览仅支持 ≤200KB 文本文件，超限或二进制显示「无法预览」并提供系统打开入口 |
| 路径逃逸尝试 | agent 工具参数含 `..` 或绝对路径时拒绝执行并返回错误信息给模型 |
| 并发多会话生成 | 各会话独立 AbortController 集合，互不影响；停止仅作用于目标会话 |
| 数据库首次初始化失败 | 启动时弹致命错误提示并退出，不写半成品数据 |

## 9. 里程碑路线图

### M1 — 可用骨架（P0 核心闭环）
- 进程骨架与 IPC 白名单全量通道；数据库 schema 与 migration。
- Provider 管理（增删改 + 测试连接）；Bot CRUD + 人设模板。
- 单聊流式对话（pi 集成层）、停止/重试、错误内联。
- 群聊编排：协调者 JSON 决策 + 兜底 + @ 提及 + 串行发言。
- 三栏 UI、Composer、消息流、深色模式基础。
- Mock provider + `npm run smoke` 打通端到端。

### M2 — 记忆 + 工作区
- 记忆注入、自动提取触发器与去重、Memory 标签页手动管理。
- 工作区目录、三个 agent 文件工具（含路径逃逸防护）、Workspace 面板（列表/预览/系统打开）。
- 消息分页、未读、置顶排序、头像上传。
- 审核规则注入、时区检测。

### M3 — 打磨与打包发布
- UI 视觉细节对齐（气泡、胶囊、叠头像、动画）、空态与引导。
- 性能优化（分页、渲染节流）、错误文案完善。
- electron-builder 打包配置（ESM banner shim、--ignore-scripts 注意事项）与安装包产出验证。
- README（含明文密钥风险声明）与发布物料。

## 10. 未纳入范围（Out of Scope）

- **账号体系**：不做注册/登录/用户中心，「我的」「市场」仅为占位入口。
- **云同步**：不做跨设备同步、不做云端备份；数据可移植性通过本地文件实现。
- **移动端**：仅桌面端（Electron），不考虑 iOS/Android 与响应式 Web 版本。
- **插件市场**：不开放第三方 Bot/工具插件生态；人设模板为内置常量。
- **语音/视频通话**：仅文本与图片附件消息。
- **多用户协作**：单用户单机应用，不做实时多人协同。
